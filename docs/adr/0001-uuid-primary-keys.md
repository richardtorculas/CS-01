# ADR 0001: UUID primary keys

- **Status:** Accepted
- **Date:** 2026-09-26
- **Story:** US-01 (first migration)

## Context

[DATABASE.md](../DATABASE.md) requires the primary-key type (UUID or BIGINT identity) to be decided before the first migration. Ids appear in URLs, tokens and offline drafts that the mobile app creates before contacting the server.

## Decision

Every table uses a `UUID` primary key named `id`, generated by the application (`uuid.uuid4`). Foreign keys are UUID columns named `<singular>_id`.

## Consequences

- Ids are not guessable or enumerable, which supports the rule that a resource the caller may not see behaves as "not found" (API.md, 404).
- Clients can generate ids offline for drafts without collision risk.
- Larger indexes and slightly slower inserts than BIGINT. Acceptable at the pilot's scale (about 1,000 reports plus users).
- Alternative considered: BIGINT identity. Rejected because sequential ids leak volume and invite enumeration.
